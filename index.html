MODULE 01 CORE AXIOMS

The Non-Negotiable Junior Dev Mindset

Three unbreakable rules for analyzing software specifications and exam scenarios.

RULE 01

"Zero Hallucination" Rule

Never assume, invent, or extrapolate features. If the client does not explicitly ask for a shopping cart, login authentication, payment gateway, or database, they are strictly non-existent.

❌ Exam Failure Trigger:

"I will add an Add to Cart button and a sticky customer login popup so users can save favorites."

✅ Senior-Approved Response:

"The brief specifies an informational showcase only. Transactional e-commerce or user state management is out of scope."

RULE 02

The "Enough vs. Not Enough" Test

Clients speak in subjective feelings; engineers evaluate hard constraints. When a client asks for "modern, clean, warm vibes", you must declare the requirement insufficient for CSS coding until exact metrics exist.

❌ Amateur Developer:

"I'll choose warm earthy brown hex codes (#8B4513) because they said warm cafe vibes."

✅ Junior Engineer:

"NOT ENOUGH. Vague aesthetic descriptors lack hex color codes, typography hierarchy, and WCAG contrast targets."

RULE 03

Semantics Over Appearance

Tags dictate document meaning and accessibility tree structure, not default visual styling. A <button> is for actions; an <a> is for navigation; a <section> requires a heading; never use a <div> soup.

❌ Div Soup Trap:

Using <div class="header-box"><div class="nav-btn" onclick="..."> for navigation.

✅ Clean Semantic Tree:

<header><nav><ul><li><a href="#menu"> with proper keyboard accessibility and landmark roles.

MODULE 02 REQUIREMENT AUDIT ENGINE

The "Is It Enough?" Audit Matrix

Click each dimension to evaluate whether a client's specification is technically actionable or dangerously incomplete.

The Core Test Question

Does the client state primary vs. secondary focus, or just dump a wish list of items?

Client Clue: "Show our 12 drinks, 6 pastries, story, address, and awards on one page."
Engineering Sufficiency Analysis

Verdict: Incomplete Hierarchy. The client provides content items but fails to define whether the Menu or the Physical Location is the primary conversion priority above the fold.

Action: Scaffold separate semantic <section> landmarks with descending <h2> headings; do not merge them into an unstructured grid.

The Core Test Question

Did they mention mobile users, touch targets, screen sizes, or device constraints?

Client Clue: "People on their phones should easily find our address and operating schedule."
Engineering Sufficiency Analysis

Verdict: Partial Sufficiency. The intent (mobile accessibility) is stated, but breakpoint values, layout rearrangement rules, and touch sizes are unspecified.

Action: Apply Mobile-First CSS architecture. Stack essential contact data above heavy media catalogs or provide sticky anchor links. Ensure 44x44px minimum touch targets.

The Core Test Question

Are exact form fields, required labels, validation states, and submission endpoints defined?

Client Clue: "Customers should be able to get in touch with our support team."
Engineering Sufficiency Analysis

Verdict: Severe Insufficiency. "Get in touch" could mean a mailto: link, a tel link, a 3-field contact form, or live chat.

Action: Never invent a database-backed contact form with CAPTCHA without explicit confirmation. If asked to scaffold, provide standard accessible <form><label for="..."> without unstated fields.

The Core Test Question

Are aspect ratios, image formats, bandwidth limits, or text contrast constraints stated?

Client Clue: "Must be fully readable for senior citizens on low-cost smartphones on mobile data."
Engineering Sufficiency Analysis

Verdict: User Persona Clear, Technical Specs Insufficient. The client highlighted constraints (seniors + low bandwidth), but didn't specify file formats or font sizing.

Action: Implement system fonts over heavy custom web font CDNs, use SVG vector icons, enforce font-size: 1rem+ with generous line-height: 1.5+, and WCAG AA contrast.

💬

Junior Dev Script: How to Argue Insufficiency Without Sounding Clueless

"While the client has articulated the high-level aesthetic intent ('warm, modern, clean') and user context, the requirement is technically insufficient to commence visual CSS styling. Specifically, the brief lacks: 1) An established brand color palette with verified WCAG 2.1 AA/AAA contrast ratios. 2) Specific typography scale and responsive breakpoint definitions. 3) Exact media aspect ratios and submission endpoints. Proceeding with arbitrary color selection risks costly visual refactors. We recommend locking the semantic HTML document outline first while requesting an approved brand asset sheet."
MODULE 03 W3C CHEAT SHEET

Standards & Architecture Reference

Deep dive into semantic markup, 1D vs 2D layout mechanics, box model physics, and responsive units.

W3C LANDMARKS

Structural Document Landmarks

Each page should have a single <main> element representing central content. Landmarks enable screen reader users to jump directly to sections.

<header> → Logo, Branding, Site-wide Navigation
<nav><ul><li><a> → Accessible list of anchor links
<main> → Exactly ONE primary content container
<section><h2> → Thematic block (MUST have a heading!)
<article> → Self-contained, syndicateable unit
<aside> → Tangentially related side content
<footer> → Copyright, operating hours, legal
FORM ACCESSIBILITY

Explicit Form Controls

Every input MUST have a programmatic label association using matching for and id attributes.

<form action="/submit" method="post">
  <div class="form-group">
    <label for="client-name">Full Name</label>
    <input type="text" id="client-name" name="name" required>
  </div>
  <button type="submit">Submit Inquiry</button>
</form>
⚠️ Rule: Placeholder is NOT a replacement for a <label>. Screen readers and users with cognitive fatigue rely on persistent labels.
FLEXBOX (1D LINEAR)

When to Choose CSS Flexbox

  • Dimension: One-dimensional (Row OR Column alignment).
  • Content-Driven: Items size according to their internal text/content rather than strict grid tracks.
  • Ideal Use Cases:
    • Navigation bars (display: flex; justify-content: space-between;)
    • Button groups, badge clusters, breadcrumbs
    • Internal card alignment (avatar + text title + button on one line)
CSS GRID (2D MATRIX)

When to Choose CSS Grid

  • Dimension: Two-dimensional (Rows AND Columns simultaneously).
  • Layout-Driven: Tracks dictate item placement and uniform sizing across the catalog.
  • Ideal Use Cases:
    • Catalogs (e.g. 12 coffee drinks + 6 pastries in auto-fit cards)
    • Overall page layouts (header / sidebar / main / footer)
    • Doctor schedule tables or calendar time slots
Architectural Rule of Thumb: Use CSS Grid for the macro container (e.g., catalog grid of menu cards), and Flexbox for micro alignments inside each individual card!

BOX SIZING FORMULA

box-sizing: border-box

Standard CSS reset rule. When specified, width: 300px includes padding and border. Without it (content-box), adding 20px padding expands the total element width to 340px, triggering mobile horizontal scrollbars!

*, *::before, *::after {
  box-sizing: border-box;
  margin: 0;
  padding: 0;
}
MOBILE-FIRST MINDSET

Linear Flow Before Media Queries

Write default CSS for small viewports (320px–480px) first, ensuring natural document flow without horizontal scrolling. Then use @media (min-width: 768px) to enhance to multi-column grids.

/* Mobile base: 1 column */
.menu-grid {
  display: grid;
  grid-template-columns: 1fr;
  gap: 1rem;
}

/* Tablet & Desktop enhancement */
@media (min-width: 768px) {
  .menu-grid {
    grid-template-columns: repeat(auto-fit, minmax(280px, 1fr));
  }
}
FLUID UNITS VS FIXED PIXELS

Unit Hierarchy

  • rem (Root EM): For font sizes, margins, and padding. Scales automatically with user OS accessibility preferences.
  • % and vw/vh: For fluid widths and hero heights.
  • Fixed px: Avoid for container widths. Use only for hair-line borders or tiny specific icon dimensions.
MODULE 04 ESSAY BLUEPRINT

The 4-Step Technical Essay Blueprint

Use this battle-tested 4-step structure to score full points in technical exams and client design proposals.

STEP 1

Direct Technical Verdict

Provide an immediate, unambiguous stance in your opening sentence. Do not waffle.

[Stance: SUFFICIENT / INSUFFICIENT / CSS GRID / REJECT] + [Core Technical Theme]
"The client's specification is insufficient to commence visual CSS styling and color selection."
STEP 2

Scenario Clues & Evidence

Cite the exact quotes or requirements explicitly present in the client's scenario.

"According to the scenario text, the client specifies..."
"The brief states only that the cafe wants a 'warm, modern, and clean' look without providing a brand guide."
STEP 3

Standards & Architectural Rationale

Explain the W3C semantics, box model physics, WCAG accessibility, or layout geometry that applies.

Cite W3C HTML5 semantics, 2D Grid vs 1D Flexbox, WCAG 2.1 AA contrast, or box-sizing rules.
"Engineering standards require hex/HSL values tested against WCAG AA 4.5:1 contrast ratios before styling."
STEP 4

Risk & Failure Analysis

Articulate what breaks if implemented poorly: layout collapse, accessibility violations, or scope creep.

"Failing to enforce this constraint leads to [Specific Technical Failure / Refactor Cost]."
"Guessing palette colors leads to visual inconsistency and costly CSS refactors once true brand assets arrive."
